# UI and Design Rules

These rules apply to all user interface work in this project; this file owns them and the authoritative wording of the target-access rule. Read it before adding or changing UI code. The mechanism behind the UI — the debug backend, the worker and session internals — lives in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Stack

- The UI is built with **Qt 6 Widgets** (`Qt6::Core`, `Qt6::Gui`, `Qt6::Widgets`) in C++23. No QML, no Qt stylesheets (QSS) and no other UI toolkit.
- The application runs on the Fusion style (`QStyleFactory::create("Fusion")`) so both themes render identically regardless of the desktop's platform theme.
- The target platform is Linux; a GUI run prefers **X11/XWayland** when a `DISPLAY` is available, so a remembered window position can be restored, with native Wayland as the fallback (see [Wayland](#wayland)).
- UI code follows the project's C++ conventions; see [`docs/ARCHITECTURE_MAP.md`](docs/ARCHITECTURE_MAP.md).
- The project ships two UI binaries: the main `slopkit` application and the `slopkit-sandbox` practice target launched from the Help menu. Both link the shared `slopkit_ui_common` static library (`ui/theme`, `ui/fonts`, `ui/platform`, `ui/settings` and `ui/components/`), so the sandbox renders with the same palette, fonts and components instead of duplicating them.

## Visual direction

- Modern and clean: generous padding and spacing, minimal borders, a restrained color palette with a single accent color, and consistent alignment.
- Do not hand-style widgets. Colors and surfaces come from the application palette; geometry comes from layouts and size hints. Do not hard-code pixel paddings or sizes.
- Prefer whitespace and hierarchy (size, weight, muted color) over lines and boxes to separate content.
- Keep motion subtle. Qt's standard control animations are fine; avoid anything flashy.

## Theming

- Dark theme is the default. A light theme must also be available and switchable at runtime.
- Define themes as data: `ui::Theme` is a struct of named semantic colors (`background`, `surface`, `surface_hover`, `text`, `text_muted`, `accent`, `accent_hover`, `accent_active`, `on_accent`, `border`, `success`, `warning`, `error`, `syntax_register`, `syntax_immediate`, `syntax_module`, `syntax_keyword`, `syntax_string`, `syntax_comment`, `syntax_number`, `datatype_signed`, `datatype_unsigned`, `datatype_bits`, `datatype_float`, `datatype_vector`, `datatype_text`, `datatype_class`, `datatype_readout`, `grid_offset`, `grid_address`, `grid_ascii`, `grid_comment`, `grid_pointer`, `grid_index`). The `datatype_*` roles spell a node kind in the ReClass window — its glyph and its `Type` cell, which a hex node leaves empty — and the `grid_*` roles colour the grid's `Offset`, `Address`, `Ascii`, `Comment` and `Pointer` fields and an array's index control; the datatype default is `text`. Both `dark_theme()` and `light_theme()` must define every role.
- `make_palette(const Theme&)` maps the roles onto the palette roles Qt paints from (`Window`, `Base`, `Button`, `Text`, `Mid`, `Highlight`, `HighlightedText`, …) for all three color groups.
- `apply_theme(const Theme&)` installs that palette application-wide, updates `active_theme()` and keeps `QStyleHints::setColorScheme` in step so native parts (file dialogs, decorations) follow.
- Never hard-code colors in widget code. Always pull from the active theme, either through the palette or through `widgets::status_color()`.
- When adding a new color role, add it to both the dark and the light theme.
- Both themes must keep readable contrast for text and for interactive states (hover, active, disabled).
- Widgets that paint themselves with an accent or status color (the primary button, the status label) must re-apply their palette when the application palette changes, so a theme switch updates them live.

## Custom components

- Build reusable widgets instead of repeating raw Qt calls. Put them in a dedicated module (`ui/components/`): buttons, panels, section headers, status labels and icon loading.
- Icons are rasterised at configure time from `assets/icons/*.svg` into multi-size PNGs and embedded as Qt resources; load them through `widgets::application_icon()` / `widgets::action_icon()`, never from disk or a theme at runtime. The ReClass node-kind glyphs (`assets/icons/datatypes/*.svg`) are the one deliberate exception to the "or a theme" half: `widgets::datatype_icon()` loads the embedded black raster and re-tints it from the active theme's datatype role, so a kind's glyph colour follows the theme at runtime while its artwork stays a build-time resource.
- Components take their styling from the active theme, expose a small and consistent API, and keep no hidden global state.
- Prefer composing existing components over adding one-off widgets. If similar Qt code appears twice, extract it into a component.
- For a single-line prompt, reuse `ui::widgets::InputBox` instead of `QInputDialog`: it is themed and parent-owned, runs an optional validator on every edit and again on accept (disabling OK and showing the validator's message while the text is invalid), and can render its field in the monospace font for addresses and expressions.
- Let Qt do the work: use `QSplitter` for dividers, `QGroupBox`/`widgets::Panel` for groups, `QProgressBar` for progress and `QTableView` with a `QAbstractTableModel` for tabular data rather than custom-painted equivalents.
- The script editor, `ui::components::ScriptEditor`, is the Add/Edit Script dialog's Lua editing surface: a `QPlainTextEdit` subclass with a line-number gutter, four-space tab stops, auto-indent, a current-line band, a matched-bracket highlight and a marked error line. Its Lua highlighting is a separate `ui::components::ScriptHighlighter` (a `QSyntaxHighlighter`) that reads every colour from the active theme, so a theme switch repaints the source instead of hard-coding any colour. It opens at least 100 mono columns wide and 18 lines tall, widening to fit a generated hook script's longest line up to a 140-column cap while its minimum stays a fixed, text-independent 60 columns by 12 lines, so typing never resizes an already-shown window. `Esc` is not a close key: the enclosing dialog swallows it, so the `Close` button or the window-manager button is the way out. `ui::components::ScriptCompletionPopup` (driven by `ScriptCompletionModel` and `ScriptCompletionDelegate`, over `script::api_catalog` and `ui::components::script_context`) offers the API, the Lua library and the document's own names as you type and on `Ctrl+Space`, accepting with `Tab`/`Enter` inside one undo step. While the caret is inside a call's parentheses, `ui::components::ScriptCallTip` shows that function's signature with the active parameter emphasised — both read the catalogue and the document only, so neither touches the target.
- The script editor's auto-indent follows the Lua block structure: `Enter` keeps the current line's indentation, adds one four-space stop when the text before the caret leaves a block open (a trailing `then`, `do`, `function`, `else` or `repeat`, or an `{`, `(` or `[` still unclosed at the caret) and drops one stop when the new line opens with `end`, `else`, `elseif`, `until` or a closing bracket; `Backspace` inside a run of four or more spaces deletes the whole stop at once, so indentation is undone a stop at a time.
- Every in-place editor applies its text on `Enter` and closes, while `Esc` and a focus loss discard it; a text the owning model refuses leaves the editor open with its text selected and the reason on the status line that surface already owns. `ui::components::ValidatingDelegate` gives a table cell that behaviour, taking the `Return` the editor would otherwise hand up to the parent, where a dialog would press its own default button; the address list's `Description` and the Memory Viewer's register table edit through it (with `ui::widgets::IndentDelegate` adding the indent painting on top), and the custom-painted ReClass grid and byte view keep their own editors on the same rule.
- Model/view code keeps its state in the model; the view is only configured once at construction.
- First sanctioned exception to the table rule: the Memory Viewer's hex view, `ui::components::MemoryView`, is a custom-painted `QAbstractScrollArea` because its per-byte change colours, its per-column hex offset header, its column width and value groupings that change with the chosen value format and text encoding, its unbounded scrolling, its inline per-cell editor and its right-click menu (a `Navigate` submenu holding Go To and Back, then the value format and text encoding submenus and text-column visibility) cannot be expressed by a `QTableView` plus a column/delegate model. It sits in the Memory Viewer's lower pane and still keeps the model/view spirit: the cache, the format/encoding, the three-block live window and the write submission live in `ui::components::MemoryViewDocument`, and the widget only lays out, paints and handles input.
- Second sanctioned exception: the Memory Viewer's instruction listing, `ui::components::DisassemblyView`, is likewise custom-painted because each row's byte text has a different width and wraps onto as many lines as the bytes column is wide (a wide pane wraps at most seven bytes per line, while the column gives up space first, down to a single byte per line, and the instruction text keeps what is left and clips), so rows have variable heights, the address column is module-relative, `??`/`.byte` rows paint muted and the instruction cursor is unbounded with its own key and wheel handling (including stepping to the next page-aligned window at the decoded bounds). Its live window, decode cache, wrapped byte lines and rendered row text live in `ui::components::DisassemblyDocument`, and the widget only lays out, paints and handles input. Its painted header band's two column boundaries are drag handles that resize the address and bytes columns (clamped so the instruction column keeps its glyphs, with the bytes column's drag cap at that same seven-byte width), and a clicked row stays selected by address — not by pixel — and paints a `theme.surface_hover` band so the target of `Toggle Breakpoint` is obvious.
- Third sanctioned exception to the table rule: the ReClass window's node grid, `ui::components::ReClassView`, is a custom-painted `QAbstractScrollArea` because its `Offset`, `Address` and `Ascii` fields are measured from the text the selected class draws and its remaining fields flow after them from one content slot — a `hexN` row's byte dump and a defined row's `Type Name = value` start at the same x — each field capped at the widest text its kind or the class can give it and drawing its text whole whenever the run was measured for it, eliding it only where the room genuinely cannot hold it (the same "does it fit" its hover tooltip reads, so no ellipsis lands on a cell that offers no tooltip), with nothing able to drag them, and it paints no header band at all, so a grid that repaints on the live cadence never asks a header to measure the model; its one editor is opened on the double-clicked `Name`, `Comment` or `Value` field of the flowed row — or over the single byte of a `hexN` dump, the `Ascii` character, the `[N]` a `Type` cell brackets or a bracketed reading of a `hex32`/`hex64` cell's `Hints` field, that the point stands for — a row's note, readings and pointer follow its own value, its rows carry the disclosure triangle of a reference node and its scroll offset and cursor survive a live pass. It still keeps the model/view spirit: the structure model owns the rows, the offsets and the inlined blocks, the value model owns the addresses, the block bytes and the writes, the proxy model fuses the two into the nine fields, and the widget only lays out, paints and handles input.
- The disassembly listing renders every address an instruction prints — a relative branch/call target or a computed memory operand — the way it renders the row's own address: `<module>+0x<RVA>` when the target lands in a file-backed image, and the decoded absolute text in the shortest digits (`0x2010`) otherwise. The form follows Settings > Addresses, so Absolute address mode prints the unpadded absolute text, and the listing, the painted text and the Copy forms all agree.
- The instruction listing's right-click menu carries `NOP Instruction` for a decoded row and `Restore Original Instruction at <address>` for a row this session replaced. One click replaces the row's whole instruction (its full decoded length) with NOP bytes (`90`), or writes the remembered original bytes back; both go through `process::AccessWorker` like the byte view's inline edit and log each attempt under the `ui` category.
- The right-click menu also carries `Edit Instruction...` and `Hook Instruction...` for a decoded row. `Hook Instruction...` opens the address list's Add Script window prefilled with a generated hook script (see [`docs/SCRIPTING.md`](docs/SCRIPTING.md)); it reads only the listing's cache, never the target, and nothing reaches the address table until the dialog's Add is clicked, so a discarded dialog leaves no row. A row that cannot be hooked reports the reason on the Memory Viewer's status line instead of opening the dialog.
- The action is refused while no target is attached, while the row is not a decoded instruction, while the instruction's bytes are not fully cached, or while a patch write is already in flight. An undecodable/`??` row shows `NOP Instruction` disabled with the explanation `Only a decoded instruction can be replaced.`, and `Hook Instruction...` shows the same way with `Only a decoded instruction can be hooked.`.
- The listing keeps decoding what the target holds, so every row inside a replaced instruction paints in `theme.warning` and the first of them paints `NOPed: <original instruction>` after its text. The patches are remembered for the Memory Viewer session only (the dialog owns the store, keyed to the attached pid) and are dropped when the attached target changes or detaches.
- Each Memory Viewer pane keeps its own navigation history. The instruction listing's right-click menu opens with a `Navigate` submenu carrying `Go To...`, `Follow` and `Follow in Memory View` for a decoded row whose instruction references an address (the first reference is used; a `.byte`, `??` or unreadable row has no `Follow` entries); both request a fresh live page, the first moves the listing's own cursor there and the second moves the byte view's while the listing stays put.
- Each pane's `Navigate` submenu also carries a `Back`, always present and disabled while that pane's history is empty, which returns it to the location it jumped from. Only an explicit jump (`Follow`, `Follow in Memory View`, `Go To...` and the pointer-chain evaluation) records; wheel/keyboard scrolling, re-layout and window-open seeding do not, and opening the window at an address clears both histories.
- The Memory Viewer's `View` and `Tools` menu bar entries repeat those listing commands and act on the instruction selected in the listing: `View` holds `Go To...`, `Follow`, `Follow in Memory View` and `Back`, and `Tools` holds `NOP Instruction`, `Restore Original Instruction`, `Edit Instruction...`, `Hook Instruction...` and `Find out what addresses this instruction accesses`. They gate exactly as the right-click menu does — the same `editable()` predicate decides NOP/Edit/Hook, a session patch decides Restore and a memory operand decides the access resolution — so the two surfaces cannot disagree about a row, and every disabled entry explains itself in its tooltip. `Restore Original Instruction` keeps its stable wording in the menu bar (the right-click entry names the address in place), with the address and the original text in its tooltip. Only `Close` (`Ctrl+W`) and the reused `Go To...` (`Ctrl+G`) carry shortcuts; the debug and listing commands have none.

- The listing paints each register name, immediate literal/displacement and module name of a `module+0x<RVA>` address in its `theme.syntax_register` / `theme.syntax_immediate` / `theme.syntax_module` role — the `0x`-prefixed RVA offset after the `+` takes the immediate role — while the `+` separator, mnemonic, prefixes, brackets, commas, whitespace and the bytes column keep the row's own colour (`theme.text`, or `theme.warning` on a patched row and `theme.text_muted` on a `.byte`/muted row).

## Fonts

- Use **Noto Sans** as the UI font. Embed it in the binary rather than loading it from disk at runtime, so the app has no external font file dependency.
- Use **Noto Sans Mono** as the companion monospace font for text that must line up (addresses, hex dumps, paths, sized fields) and apply it only to those widgets.
- Every machine read-out uses the mono face: the Memory Viewer's hex dump and instruction listing, the Address List and scan-hit tables, the register and call-stack tables, the scanner's address and value fields, the Process List PID, the Add/Edit Script dialog's Lua editor, and the debugger's read-outs — the Breakpoints window's `Size`, `Address` and `Hits` columns, both Access Watch tables (`Recorded accesses` and `Instruction accesses`), the Memory Viewer's debug status line, the Access Watch header and hint lines, and the ReClass window's class header line and its `Address`, `Offset`, `Ascii`, `Value`, `Hints` and `Pointer` fields.
- Word and prose-only read-outs keep the UI font even inside those surfaces: the Breakpoints window's `Kind` column, the Access Watch `Access` column, the Access Watch status line and the Breakpoints hint line.
- Embedding happens at build time through a CMake script that converts the `.ttf` into a generated C++ header. Do not commit generated headers or paste font byte arrays into source files.
- Keep the source font under `assets/fonts/` (e.g. `NotoSans-Regular.ttf`) and track it in version control together with its license (OFL).
- The CMake script (e.g. `cmake/EmbedFont.cmake`) should:
  - Read the file with `file(READ ... HEX)` and convert the hex string into a comma-separated `0x..` byte list.
  - Write the result into the build directory (`${CMAKE_BINARY_DIR}/generated/`) as a header containing a `constexpr unsigned char[]` and a size constant.
  - Re-run automatically when the font file changes (e.g. `set_property(DIRECTORY APPEND PROPERTY CMAKE_CONFIGURE_DEPENDS <font>)`, or `add_custom_command` with `DEPENDS`).
  - Be exposed as a function such as `embed_font(<target> <font_path> <symbol_name>)` that also adds the generated include directory to the target.
- Register the embedded faces with `QFontDatabase::addApplicationFontFromData` and expose them as `ui::ui_font()` / `ui::mono_font()`; the application font is set once, at start-up.
- Additional weights (Bold, Medium), a monospace companion or icon glyphs go through the same `embed_font` function; do not add a separate embedding mechanism.
- Qt selects glyph coverage from the font itself, so no glyph ranges need to be requested explicitly.

## Number notation

- Every hexadecimal read-out of an address, a register or a decoded instruction prints an explicit `0x` prefix in upper-case digits: an instruction operand (`MOV EAX, 0x1000`, `[RBP-0x4]`, `JMP 0x401000`), an undecodable byte row (`.byte 0x90`), the disassembly listing's address column and its operands and Copy forms (`0x2010`), a module-relative address (`app+0x40`) and an absolute address (`0x7FFD1234`). Instruction operands, the listing's address column and the Access Watch operand column print the shortest digits — no address-width or type-width zero padding — while the byte view's gutter and header, the scanner's `Start`/`Stop` range fields, the Breakpoints `Address` column, the register values and the debug tooltips keep the 16-digit pane form (`0x0000000000001234`). The prefix is added in front in both cases. The ReClass grid's rows are the one deliberate exception, spelled bare in the ReClass entry below.
- A data value (`1A2B`), a log record, the headless-CLI output, the practice target and the `.skt` table-file text keep their bare upper-case digits, and so do the listing's raw bytes column (`48 89 E5`) and the Memory Viewer's hex dump, which are not addresses.
- The ReClass grid's rows are the deliberate exception above: the `Address` and `Offset` columns and a `hexN` value cell's byte dump stay bare and carry no `0x`, and every other hex read-out in a row is the shortest digits it needs. The `Address` column draws bare upper-case hex (`400020`), right-aligned on the column's content box so addresses of different lengths line up at the low end, and only as wide as the widest address the class draws — the model's own wording (`not resolved yet`, `?`) while an address is missing — and the class header line and the class tooltips spell an address the same way. The `Offset` column prints bare upper-case hex without padding (`14`), and a `hexN` value cell keeps its zero-padded, space-separated byte dump (`1A`, `1A 2B`, eight pairs for a `hex64`), which is a dump rather than a number, while the raw-bits reading beside that dump carries the prefix on its shortest digits (`(-999998.999) (-2147483648) (0xFFFFFFFF)`). An integer's hex alternative is the shortest digits of the kind, wrapped in parentheses and prefixed (`42 (0x2A)` for an `Int32`, `-1 (0xFF)` for an `Int8`), and shown as hex the alternative leads bare while the decimal moves inside the parentheses (`0x2A (42)`), a `pointer` or `class_pointer` cell draws `-> <TAG>` followed by those digits (`-> <HEAP>1A2B3C4D`), and the `Ascii` column is sized from the row kinds, capped at the eight characters a cell draws, so a wider node no longer stretches the row while the whole reading stays on the cell's hover. The inline value editor still prefills the kind-width padded form (`0000002A`) and a `Copy` still writes the 16-digit absolute address, because neither is a row read-out.
- A field the user types an address, register or instruction number into reads bare hex as hex, `0x…` as hex and `#…` as decimal, so the text the app prefills from its own output round-trips. This covers the scanner's Start/Stop range, the Memory Viewer and Disassembly Go To prompts, the Add Address and Breakpoints dialogs, the register cell and the instruction editor, and a legacy `.skt` file that stored `address=0x…` still loads (a newly written one keeps the bare `address=`).
- The scanner's `Hex` checkbox converts what the `Value` and `Upper value` fields already hold when it is toggled: each field is re-read in the base it was in and rewritten in the other (plain decimal digits or bare upper-case hex with no padding). A field that cannot be re-read — empty, malformed, or a value type with no such form, such as hex for a float — is left exactly as typed.
- The module-relative `module+0x<RVA>` form carries the prefix on its RVA (`app+0x40`), and the shortened display label and the untruncated Copy spelling agree on it. Fields that are decimal-only — the fast-scan alignment step, hit counts, sizes and PIDs — stay decimal.
- The scanner's fast-scan `Alignment` field is prefilled from the selected value type's width (`1` for `Byte`, `2` for `2 Bytes`, `4` for `4 Bytes`/`Float`, `8` for `8 Bytes`/`Double`) and follows a value-type change unless the user typed a custom step, and the value-type list offers no `All` entry (a legacy `All` table member loads as `4 Bytes`).
- A base may also be a **symbol** a script registered (see [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)): the field resolves a bare name, or a `<symbol>+<offset>` expression, to the symbol's live 64-bit value. A base is resolved as module name → symbol name → literal, so a loaded image is never shadowed while a symbol literally named `deadbeef` still wins over the bare-hex reading, and an unknown name fails like an unknown module.
- An address field also accepts a **pointer chain** with square brackets: a `[` … `]` group closes with one pointer dereference and nesting spells a multi-level chain (`[[game.exe+0x10]+0x18]+0x24`), while a bracket-free expression keeps the legacy rule (one dereference between consecutive `+` offsets). A bracketed expression is always resolved live by the worker — the Go To, Add Address and `.skt` parsers shortcut only a level-free `module+offset`, so `[0x120000+0x10]` is submitted instead of read as `base + 10`.
- The `Add Address` dialog adds an expression that does not resolve *yet*: an unknown module or symbol or a pointer chain without an attached target parses, so the row is added with the expression kept and its address left unresolved (`0`, "the last successful resolution"), and the address list's existing re-resolve fills the address in once the target or symbol appears. A **parse** error — malformed text such as `app+`, `[]` or an empty field — is still refused, keeping the dialog open with `Address: <reason>`. The same dialog serves `Edit Entry…` (value rows only) as `Edit Address` with a `Save` submit: it opens prefilled from the row (description, the stored expression or, when the row has none, the resolved absolute address, type, size in bytes and `Show as hex`), its preview resolves the prefilled field like Add, and `Save` overwrites exactly those fields in place while the row's identity, kind, nesting and `Active` state stay untouched. An unresolved-but-parseable expression is accepted and stored here too, and `Close`, `Esc` or a parse error leave the row unchanged. The dialog groups its fields into an `Address entry` panel (the description, address and read-out strip) and a `Value format` panel (the type, size in bytes and `Show as hex`), and `Enter` anywhere in the form submits it as `Add`/`Save` while `Esc` keeps closing it.
- A module name is shortened **for display** once the part before its file extension exceeds 16 characters: it keeps its first 6 and last 5 characters around `...`, and the extension is always kept (`DyingLightGame_TheBeast_x64_rwdi.exe` → `DyingL..._rwdi.exe`). The rule lives in one function, `ui::elide_module_name`, and applies to the scanner's module dropdown and to the module name inside every rendered `module+0x<RVA>` (the listing's address column and operands, the byte view, the address list, the found list, the call stack and the Access Watch tables). The untruncated spelling is what Copy writes and what the address parser, Go To, the Add Address dialog and the `.skt` lookups accept, so a copied address still resolves.
- The address list's `Address` column paints the resolved address, never the stored expression: a row echoes the same `module+0x<RVA>` or absolute text as every other address surface, and a row whose expression has not resolved yet reads `0x0`. The stored expression stays untruncated in the `.skt` text and the dialogs' fields; the cell's tooltip names it (see below).
- Hovering a shortened module name reveals the untruncated text: the full name on a dropdown entry and in the scanner's collapsed box, and the full `<module>+0x<RVA>` on an address surface (the listing and byte view address columns and the listing's operand runs, and the address-bearing table cells through `widgets::kFullTextRole`). A surface that did not shorten shows nothing new, and a table cell's own `Qt::ToolTipRole` message takes precedence over the full text. Hovering an address-list row that has a stored expression reveals that untruncated expression followed by the resolved absolute address on the next line.

## DPI and scaling

The UI must look correct on standard, HiDPI, and fractionally scaled displays, and must update when the scale changes (for example when the window moves to another monitor).

- Qt owns device-pixel-ratio and fractional scaling. Do not read a scale factor, do not multiply sizes by one, and do not re-create widgets when the scale changes.
- Specify all sizes, paddings, spacing and fonts in logical units (the base design at scale 1.0). No raw pixel literals that encode a scale.
- Never assume widget size equals framebuffer size, and never compute it; layouts and the platform handle the conversion.
- Support fractional scales (1.25, 1.5, 1.75, and so on) without blurry text or misaligned layout. Do not round the scale to an integer.
- Do not hard-code assumptions about a single monitor's DPI. Use layouts that adapt and a sensible minimum size instead.

## Wayland

Wayland is a supported target, but a GUI run prefers **X11/XWayland** whenever a `DISPLAY` is available, because a Wayland compositor owns a top-level window's position and drops a requested one, so a remembered window frame (see [Windows, dialogs and layout](#windows-dialogs-and-layout)) can only be restored on the X11 platform. Native Wayland is the fallback for a session where the xcb platform plugin cannot load.

- The choice is one rule, `ui::preferred_platform_spec()` (applied by `ui::prefer_platform_with_remembered_positions()` before the `QApplication` is built), which selects `QT_QPA_PLATFORM=xcb;wayland`; native Wayland is then used only if `xcb` cannot be loaded.
- An explicit `QT_QPA_PLATFORM` is never overwritten, so native Wayland can be forced with `QT_QPA_PLATFORM=wayland slopkit`; with no `DISPLAY`, no variable is set and Qt's own default stands.
- Set `QGuiApplication::setDesktopFileName("slopkit")` so compositors, taskbars and desktop entries match the window correctly. The ID must match the `.desktop` file name and its `StartupWMClass`.
- Load the window icon from the generated `:/icons/<N>x<N>/apps/slopkit.png` resource so every size is available to the compositor.
- Menu action glyphs are embedded the same way under `:/icons/actions/<N>x<N>/<name>.png` and reached through `widgets::action_icon()`; the ReClass node-kind glyphs live under `:/icons/datatypes/<N>x<N>/<name>.png` and are reached through `widgets::datatype_icon()`.
- Respect Wayland limitations; do not write code that depends on them:
  - Clipboard and drag-and-drop go through Qt's standard paths. Do not talk to the display server directly.
- Window decorations may be client-side or server-side depending on the compositor. Do not draw custom title bars unless explicitly requested, and do not assume a fixed decoration size.
- Scaling on Wayland is per-output and can change at runtime. Follow [DPI and scaling](#dpi-and-scaling) and test with fractional scaling enabled.
- Do not use X11-specific APIs in UI code. Keep any platform-specific code isolated behind a small interface.

## Windows, dialogs and layout

- The main window is a `QMainWindow` with a menu bar, a single full-width scan-progress bar above the central split zones, and a status bar; the window must be resizable and carry a sensible minimum size.
- The menu bar holds exactly `File`, `View` and `Help`. `File` holds the process/table commands, `View` holds `Log`, `Settings`, `Breakpoints`, `Access Watch` and `ReClass`, and `Help` holds `Launch Practice Target` then `About slopkit`; there is no `Edit` menu. `Undo Scan` is a scanner-panel button; `Add Address Manually…`, `Add Script…` and `Table Settings…` live in the address list's table-area context menu (see below), never as menu-bar actions.
- The Memory Viewer adds its own `QMenuBar` above its split, holding exactly `File`, `View`, `Tools` and `Debug`: `File` holds `Close` (the window-scoped `Ctrl+W`), `View` holds the byte view's `Go To...` then `Follow`, `Follow in Memory View` and `Back`, and `Tools` holds the listing's `NOP Instruction`, `Restore Original Instruction`, `Edit Instruction...`, `Hook Instruction...` and `Find out what addresses this instruction accesses`. The main window's bar and its actions are untouched, and the two bars never share an action.
- The file commands are reachable from the menus and carry window-scoped shortcuts: `Ctrl+T` picks the process, `Ctrl+O` opens an address table and `Ctrl+S` saves it; they fire only while the main window is focused.

The checkbox is a request: unless the hook accepts, the flag is left as it was, the box snaps back and the refusal (the hook's message, or `activate() is not defined`) is reported on the status line as `Activate failed: <message>` / `Deactivate failed: <message>`. While the box stays ticked the script's optional `update()` runs once per `Live update` interval, and a failed tick switches it off — its `deactivate()` runs and the box clears — reporting once as `Update failed: <message>` on the status line. Its row menu offers `Run Script`, `Edit Script…` and `Delete`; the value-row commands (Change value, Active, Show as hex, Browse this memory region) and the watch commands do not apply to it and are not shown. `Run Script` needs an attached target, runs one script at a time and reports the script's printed lines through the log and a short outcome on the status line. The Add/Edit Script dialog offers `Verify`, an ordinary secondary button with no shortcut that compiles the edited source without running it and without touching the target: it shows `Syntax OK.` on success, or the compiler's own message on the status line with the offending line marked in the editor. The address list's right-click menu also carries the table-area commands `Add Address Manually…`, `Add Script…` and `Table Settings…`: on a row they follow that row's own entries after a separator (a value row's and a script row's alike), and a right-click below the last row shows them alone and leaves the current selection untouched.

The pass submits nothing while live update is off, while no target is attached, while there is nothing displayed or while a pass is still in flight, so an idle window stays silent. The same poll then asks each registered live ticker; the ticked scripts' `update` pass (`ui::ScriptUpdates`) is the only one — it follows that same toggle and interval, is submitted after the read pass so a slow hook can delay at most one batched read, and adds no job while no script is ticked.

A muted hint line under the strip names the accepted syntax (a module, symbol or hex base with `+0x` offsets, and `[bracketed]` pointer chains). As the user edits, a one-shot debounce (about 250 ms, restarted per edit and stopped once the text settles — never a periodic timer) resolves the text and reads the value at the resolved address through `process::AccessWorker`, painting `<module+RVA | absolute hex> = <value>` with the address in the module-relative notation above and the value in the Value format (the chosen type and `Show as hex`). Resolution is the same split as Add — a deref-free expression resolves on the UI thread with no target access, a bracketed one goes to `submit_resolve_expressions` — and the read is one `submit_read_many` submitted only while a target is attached. An expression that cannot be resolved paints a muted `not resolved yet` / `a target is required` note, an unreadable value a `?`, never an error dialog; the form resets on every show in Add mode, while an `Edit Entry…` prefill survives it, and a completion for an edit, a module map or an opening that has been superseded is dropped by job id.

The splitter puts the project tree, `ui::components::ProjectView`, on the left — a `QTreeWidget` whose two top-level groups are `Classes` and `Enums`, carrying the class context menu (`Add Class…`, `Rename Class…`, `Set Class Address…`, `Delete Class`, `Remove Unused Classes`, `Class Hierarchy View`) and the enum context menu (`Add Enum…`, `Edit Enum…`, `Delete Enum`) — and the node pane on the right: a mono header line naming the class, its expression and its resolved address, then the node grid over the nine fields `Offset`, `Address`, `Ascii`, `Type`, `Name`, `Value`, `Comment`, `Hints` and `Pointer`. The status strip carries the window's status line in its left slot, the attached-process label and then `Close` as permanent widgets. The `View` menu toggles `Class Hierarchy View` — which nests the classes a class refers to under it, guarding a cycle — beside `Expand All` and `Collapse All`. Exactly one class is shown at a time — picking a class in the tree selects it — and an expanded class reference indents that class's own fields beneath its row, so a pointer can be walked without leaving the window. An expanded array node shows one element at a time — the element row the index names and none of the others — and that index stands in the array's `Type` cell between two arrows (`Array<UInt8> [8] ◀ (2) ▶`): a click on `◀` or `▶` steps the element back or on and wraps at both ends — a quick second click that arrives as a double-click steps the element again rather than folding the row it lives in, which only the disclosure triangle folds — hovering one explains the element it shows (`Show element 8 of 8`, `Show element 1 of 8` at an end) and takes the pointing hand, and an array of one element still draws the control with nowhere to step. The index is view state keyed to the node like its expansion — 0-based, always inside `0 … count - 1`, clamped when a count shrinks, dropped when the node stops being an array and reset with the node's expansion when the class changes — and it picks which element's own `Offset`, `Address`, `Value`, `Hints` and `Pointer` the grid shows, so a `class_wrapper_array` element reads at `array offset + index × class size` inside the parent's bytes and a `class_instance_array` element at the pointer's target `+ index × class size`. An element is identified by its place in the array rather than by a name of its own, so its `Name` cell draws nothing, takes no editor and refuses a rename with `An array's element takes no name.`, and an element a grown array appends is minted without one; the fields a class array inlines are the class's own nodes and keep their names. `Add Class…` creates a class that already covers 1024 bytes of the same `hex64` padding `Add Bytes…` appends, so a new class starts as a page of the target the user retypes, and every address the window prints — the `Address` column, the header line and the class tooltips — is the shortest upper-case digits the address needs, with no `0x` and no zero padding, whatever Settings > Addresses says. The grid is zebra-striped and colour-coded from the active theme: the `Offset` column takes `theme.grid_offset`, a resolved row's `Address` column `theme.grid_address` (muted while the class address is unresolved or the block was not read), the `Comment` field `theme.grid_comment`, the `Type` cell the kind's own datatype colour (`ui::datatype_colour()`) but nothing for a hex kind, the readings a `hex32`/`hex64` cell draws beside its bytes in the `Hints` field `theme.datatype_readout` and the `Pointer` field `theme.grid_pointer`, an array's index control — its two arrows and the bracketed index between them — `theme.grid_index`, while a marked reference row (`unknown class` / `cycle`) stays `theme.text_muted` and a `Value` cell whose own bytes moved since the last pass takes `theme.warning` on just the byte pairs that moved — its whole text when the kind draws no byte pairs — while the `= ` marker that names the value keeps the cell's own colour. The grid paints its rows itself: it has no header band and its `Offset`, `Address` and `Ascii` fields stand on their measured columns at the row's head, their text aligned on the column's content box so the gap after them is the same on every row and a defined row keeps its `Ascii` cell, the row's bytes as text, while everything the row itself says flows after them from one content slot: a `hexN` row draws its byte dump there and a defined row draws its `Type Name = value` there, so the two kinds line up where the bytes are. Each row's own note (the marker `//`, followed by the note when the node has one) starts immediately behind that row's value and is widened to the widest note the class draws, its readings follow the note and its pointer follows the readings, on a narrower gutter than the fields before them, so a row reads as one line of text and a longer value or note carries its annotations further right. Every field is sized from the class rather than from the pane — the `Address` field as wide as the longest address its rows show, the `Offset` field as wide as the longest offset the class draws, the `Ascii` field as wide as the bytes the widest row's kind can put there, the `Type`, `Name` and `Comment` fields as wide as the widest text the class draws, the `Value` field as wide as the widest value a shown kind can draw and the `Hints` field as wide as the widest reading a `hex32`/`hex64` cell can draw — while the `Pointer` field is as wide as the widest pointer text it can be given; each of those widths is also the cap its run is clipped at, so a live text longer than its cap stays put and is readable from the row's tooltip. No field is clamped and none gives way: the grid shows its horizontal scrollbar only while the widest row the class draws runs past the pane, and its span ends just behind that row's last drawn field plus the pane's own margin, so every drawn reading stays reachable, while a class whose drawn text fits scrolls nothing and shows no bar. A pass that moves a value therefore re-measures only the span the bar covers, never the columns, so the view it just wrote is not re-laid-out, and clearing the cursor leaves the commands that act on a node disabled with their own explanation. The window is a registered `LiveSurface`: it adds no timer of its own, submits nothing while hidden, while live update is off, while no target is attached or while a read is in flight, and paints `?` for a block it could not read — or one whose address moved since it was read — and `Attach to a target first.`/`not resolved yet` in the address column when there is no target or no resolved class address. Its row menu carries the node commands — `Insert Node` (a node inserted with a type is named automatically - `N` and its own id, zero-padded to eight digits, `N00000001` - while a hex node stays unnamed, so the window never invents a `field_1C`), `Change Type` (which names a node that had no name of its own and pads the freed bytes with hex nodes so the following offsets do not move), `Add Bytes` and `Insert Bytes` (the 4/8/64/256/1024/2048/4096 presets and the `X bytes…` prompt the toolbar's drop-downs also offer), `Edit Name`, `Edit Comment`, `Show as hex`/`Show as decimal`, `Copy`, `Dissect`, `Follow Pointer`, `Previous Element`/`Next Element` (which walk the row's array and are dead with their reason on a row that is not an array and on an array of one element), `Delete`, `Create Class from Nodes`, `Shrink Class`, `Copy Address`, `Copy Nodes`/`Paste Nodes`, `Hide Nodes` and the `Unhide Nodes`/`Unhide Child Nodes`/`Unhide Nodes Above`/`Unhide Nodes Below` commands, `Search for Equal Values`, `Find Out What Writes This Address` and `Find Out What Accesses This Address`, the window-scoped `Del` — and every entry explains itself through `widgets::show_explanations`. The grid itself answers `1`–`8`, which insert that many bytes at the cursor row exactly as `Insert Bytes` does — in front of the node, or at the head of the class — and are inert with no row selected, and `Ctrl+1`/`Ctrl+2`/`Ctrl+4`/`Ctrl+8`, which retype the cursor row as a `hex8`/`hex16`/`hex32`/`hex64` node through the same command and wording as `Change Type`; unlike the window-scoped `Del`, these keys live on the grid, so they fire only while it holds the focus and never steal a digit from the class name field, the byte-count prompt or an in-place editor. A right-click selects the row under the cursor before the menu opens — while at most one row is selected, as the reference does — so a command acts on the row it was opened over. The `Ascii` column prints the row's own bytes as text — a printable byte as itself and every other byte as `.`, an empty cell for a kind without bytes and `?` for a block that was not read — at most the first eight of them, the cell's whole reading staying on its hover. A `Value` cell draws the node's kind the way the reference does, behind a `= ` marker: an integer beside its parenthesised hex alternative (`= 1337 (0x539)`, `= 0x539 (1337)` once the node is shown as hex), a float at three decimals, and `bool`/`char`/`hex8`/`hex16` as their own value, while a hex cell draws its own byte pairs there and a `pointer` cell leaves the cell empty. What a `hex32`/`hex64` cell's bytes would also read as moves into the `Hints` field, each reading in its own pair of parentheses one space apart and every one of the three always drawn — the float at three decimals or, when the bytes are no usable float, the spelling that names them (`NaN`, `Inf`, `-Inf`), the signed value and the raw bits with the same prefix (`(0.000) (42) (0x2A)`, a zero cell `(0.000) (0) (0x0)`, `(NaN) (-1) (0xFFFFFFFF)`) — and the address such bytes plausibly name is the `Pointer` field's too, drawn there from the memory map's regions as `-> <CODE>0x…` — `CODE` for an executable mapping, `STACK`, `HEAP`, `DATA` or `ETC` for the rest — while an address that lands in no readable region draws nothing there, and a `pointer` cell's own arrow sits in the same field, leaving its `Value` cell empty. Every row's `Name`, `Comment` and `Value` cells are edited in place — the `Value` cell only for a kind that can be typed into — and so are a single byte of a `hexN` cell's dump, an `Ascii` character, the `[N]` a `Type` cell brackets — a text node's length in characters or an array's element count — an array's bracketed index, and any one of the bracketed readings a `hex32`/`hex64` cell draws in its `Hints` field: a double-click on the cell, on a byte pair, on an `Ascii` character, on the run, on the index or on a reading opens the editor over exactly that, prefilled with the value alone rather than with the alternatives drawn beside it, with a byte as its own two bare upper-case hex digits, the run with its bare number, the index with its bare `2` and a reading with the text it is drawn with, which it reads back in the base that reading is drawn in — the integer in bare decimal digits or behind an `0x` prefix, the raw bits in bare hex or behind `0x`, and the float as a decimal float or as the `NaN`/`Inf`/`-Inf` it drew, none of them following the node's own `Show as hex` — so a prefill round-trips, `F2` opens the name of the cursor row, `F3` its comment and `Enter` its value, and the key that commits the editor stops there instead of reaching a dialog's own default button. A note is trimmed free text — an empty one clears the node's note, reported as `Comment saved.` / `Comment cleared.` — and a name is free text the same way, so an empty one clears the node's name, reported as `Node renamed.` / `Node name cleared.`, leaving the `Name` cell drawing nothing (an unnamed row then draws no name run for `F2` to sit on, so the inline name editor, like the note's marker-only one, opens wide enough to be typed into); while a byte field takes exactly one byte (one or two hex digits, an optional leading `0x`, or `#` before a decimal 0-255) and submits a one-byte write at the node's own address plus that byte's index, leaving the row's other bytes alone and showing the byte it wrote at once. A write or an edit that is refused — no target, an unresolved address, an unread block, a kind that cannot be typed into, a byte the node does not cover, a reading of a kind that draws none or of a row whose `Hints` field elides its text, a text a byte field cannot read (`Byte: expected one hex byte such as 1A.`) or a reading cannot read (`Integer: malformed number`), a `[N]` run that is not a whole number of at least one (`Length: expected a whole number of at least 1.` / `Count: expected a whole number of at least 1.`, an index that is not a whole number `Index: expected a whole number.`), or a write already in flight — says why on the status line instead of writing a guessed address; the editor stays open on the typed text after a refusal so it can be corrected, and a rename, a note or a length/count edit touches no target and needs none. A `Paste Nodes` clones whole sub-trees, so a container's children come with it and every pasted node gets a fresh id. The two byte commands offer the reference's presets — 4, 8, 64, 256, 1024, 2048 and 4096 bytes — beside an `X bytes…` prompt, and both step over the selection: `Add Bytes` appends behind the selected node's container (or the class) and `Insert Bytes` inserts in front of the selection, so the nodes that follow keep their offsets. The row menu enables them only where they can act, as the reference does — `Add Bytes` needs a selected node and `Insert Bytes` exactly one — while the toolbar's two drop-downs stay enabled and fall back to the class when nothing is selected, appending at its end and inserting at its front. A hidden node collapses to a single `...` row: the grid draws the placeholder at the head of the row's own content slot and nothing else on it, the row inlines nothing and carries no expander, and a click on it unhides the node, while the nodes after it keep their offsets because a hidden node still occupies its bytes. `Search for Equal Values` hands the node's shown value to the scanner's value field and `Find Out What Writes This Address` / `Find Out What Accesses This Address` hand the node's address and width to the Access Watch, so none of the three reads the target from the ReClass window.

## Threading and target access

- UI code must never touch a `process::Session` and must never call a plugin or perform a syscall. Every target access — process listing, attach, module/thread probing, the desktop-entry index, memory reads, memory writes and the freeze pass — is submitted to the background `process::AccessWorker`. The byte view's inline value edit and the disassembly listing's `NOP Instruction` / `Restore Original Instruction` code patches are both memory writes and both go through that worker.
- Submit a job and stay responsive: the last known data stays visible while a job is in flight, and the affected control is disabled and relabelled or a small busy label reports the work (the Process List's `Attaching...` button). The Process List picker is the deliberate exception: it reports a still-current failure on its Details message line rather than on a status line. The scanner panel is the other exception: it reports through the log window (`View > Log`). The completion is applied by `AccessWorker::drain()` on the UI thread.
- The scanner panel keeps asking for the memory map while a target stays attached, so one failed module fetch cannot leave every address surface on raw hex for the rest of the session. A failed attempt is inert — the last applied module list, the scan range and the module dropdown stay as they were and only a successful fetch applies the memory map and publishes `memoryMapApplied`, regions included — and at most one request is in flight. The retries are rate-limited (250 ms after the first failure, doubling to a 5 s cap), stop when the target changes or is cleared, and touch the log only on the first failure of a target: later attempts are debug records, so a retry loop never floods `View > Log`.
- The worker reports a queued completion through its completion hook, which only calls `ui::CompletionNotifier::post()`; the notifier coalesces the wake-up and the queued Qt event drains the completions. The hook runs on the worker thread and must never touch a widget.
- Match every completion against the pending job id and ignore stale results (a changed selection, target, page or removed entry), so an out-of-order result never corrupts the view.
- The live value pass batches the addresses the visible surfaces show into one `submit_read_many` job, so one interval costs one job and one session lock; a per-address failure never aborts the rest of the batch. Stored address expressions are re-resolved the same way: one batched `submit_resolve_expressions` job per interval, keyed by entry id, where each failure keeps the entry's last good address and is dropped silently.
- A pass repaints only the cells whose text moved, and a column a live pass rewrites is never content-measured: `ResizeToContents` would make the header walk every row again on each pass a value changes, so the ReClass grid paints its own rows, measuring its leading fields and its flowed fields' caps from the text the class draws, so no header ever measures the model on a pass.
- Only the UI thread touches widgets; the worker thread touches neither.
- `Pause the game while scanning` suspends the target through the access worker (the `suspend` job) immediately before a scan starts and resumes it (the `resume` job) as soon as the engine stops running — finished, failed, cancelled or reset by `New Scan` — so the target is never left stopped and a session that performed the suspend resumes its target when it closes. A refused or failed suspend still starts the scan against a running target and is logged once under `scan`; the option is enabled only while a target is attached, its plugin can suspend and no debug session is running, and each blocked state explains itself in its tooltip.

## Debugger, breakpoints and access watch

The Memory Viewer's right-hand pane holds only the editable register table and the call stack of the stopped thread; it carries no pane title, because the two tables name themselves with `Registers` / `Call stack` section headers. All the run controls live on the one-line **debug control bar** at the top of the listing column, above the `Disassembly` listing it shares that column with: the leftmost widget is the single dynamic `Start Debugging` / `Stop Debugging` toggle, followed by `Toggle Breakpoint` (acting on the instruction selected in the listing), `Resume`, `Break`, `Step Into`, `Step Over`, `Step Out` and `Breakpoints...`. Every control is enabled strictly by the session state, the bar only submits work to the debug controller and renders what it reports, and the listing keeps only its own selection; the debugger's state and error text lives on the Memory Viewer's own bottom status line. `Step Out` runs the stopped thread out of its current function: it arms one transient hidden software breakpoint at the caller's return address, resumes, and reports an ordinary stop in the caller, or warns when the call stack has no caller frame.

The `Debug` menu of the Memory Viewer's menu bar mirrors that bar entry for entry — `Start Debugging`/`Stop Debugging`, `Toggle Breakpoint`, `Resume`, `Break`, `Step Into`, `Step Over`, `Step Out`, `Breakpoints...`, then `Remove All Breakpoints` — with the same wording and enablement, and reads the same shared mapping (`ui::panels::debug_enablement()`) as the bar, so the two surfaces can never disagree about a session state; the one-line bar stays where it is. The menu's `Breakpoints...` is relayed into the bar's own request, so the main window's single wiring opens the Breakpoints window for both. `Remove All Breakpoints` reuses the controller's `clear_breakpoints()`, with no confirmation prompt (the same call the Breakpoints window's `Clear All` makes) and disabled with `No breakpoints to remove.` while no breakpoint is armed — deliberately unlike that window's always-live `Clear All`. Every disabled entry explains itself in its tooltip.

Clicking the toggle while idle attaches and leaves the target **running**: the status line reads `Running...`, the toggle flips to `Stop Debugging`, `Step Into` / `Step Over` / `Step Out` / `Resume` are disabled and `Break` is enabled, and the register and call-stack tables stay empty until the first deliberate stop. Clicking the toggle again stops the session; `Break` performs the ordinary stop, after which the bar behaves as it always has.

The session can also be started from outside the pane: `Find out what writes this address` / `Find out what accesses this address` in the address list and the scan results, and `Find out what addresses this instruction accesses` in the listing. Each such command asks first — a themed Yes/No prompt naming the target, warning that the process will see the tracer, and defaulting to `No` so `Enter` never starts `ptrace` — and reports the attach, its failure and a cancellation in the main status line. While the attach is in flight the requested watch is remembered and armed once the session runs; a declined or failed prompt arms nothing and opens no window.

`View > Breakpoints` and the control bar's `Breakpoints...` button open the same non-modal Breakpoints window (`Enabled`, `Kind`, `Size`, `Address`, `Hits`, with Add Breakpoint..., Remove and Clear All). Those controls work while the target runs.

`View > Access Watch` opens the non-modal Access Watch window: a header line (`Watching <module>+0x<RVA> · writes · 4 bytes · N accesses`), a **Recorded accesses** table (instruction, code, thread, count) with `Follow in Memory Viewer`, `Stop`, `Clear` and `Close`, and an **Instruction accesses** table (address, operand, width, read/write) with `Watch writes` / `Watch accesses` and a hint line. The status line reports a failed arming (no free slot, an address already covered). Both the address list and the scan results offer `Find out what writes this address` and `Find out what accesses this address` inside a separate `Watch accesses` submenu (after a separator) in their row menus, disabled with `Attach to a target first.` while no target is attached, and the listing adds `Find out what addresses this instruction accesses` to its row menu for any row with a memory operand (a row without one keeps the entry disabled with `Only an instruction with a memory operand can be resolved.`). The listing command's hint reads "Resolved from the registers at <instruction>" for its capture and warns only when the registers could not be read or an operand names a register the backend does not report.

The bookkeeping behind these controls — the maintenance stop, the capture-registers stop, access-watch slot sharing, the backend/worker split and the attach gate — is mechanism, explained in [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

Deliberate deviations from the rules above, recorded here rather than taken silently:

1. `View` holds a third entry, `Breakpoints` (and a fourth, `Access Watch`), after `Log` and `Settings`.
2. The Memory Viewer's bottom status line carries the debugger's own state/error readout and a refused byte-view cell edit or register write (`Value: …`): a debugger has to show `Not debugging` / `Stopped at <address> (breakpoint N)` / `Running...` and the failing operation inline. The same records are written under the `debug` log category, so the report-through-the-log rule still holds in substance.
3. [Threading and target access](#threading-and-target-access)'s "every target access goes through `process::AccessWorker`" becomes "...through the access worker or the debug worker", because `ptrace` cannot run on the shared access worker (a tracee may only be ptraced by the thread that attached it). The Access Watch window's instruction reads stay on the access worker.
4. No new timer and no new accelerator is added: the pane and the Access Watch window react to the controller's signals and to the existing completion notifier and tick drain, and the run controls are the text-labelled buttons the component library already provides.
5. The Access Watch window is a normal non-modal companion dialog owned by the main window: `View > Access Watch` is the way back to it after closing it, the watch itself keeps running while the window is hidden, and its hits are coalesced into one row per instruction so a tight loop cannot flood the table.
6. The address list's view is a `QTableView` subclass, `ui::components::AddressTableView`, that resolves a drag into a nest or an insert and paints the nest band itself while holding the transient drag target, because a plain `QTableView` cannot express the "drop on the middle nests, drop on an edge inserts" gesture. The band is drawn from the palette's `Highlight` at reduced alpha and the indent from the style's `PM_TreeViewIndentation`, so both themes and every scale factor are respected, and the rows themselves still come from the model.
7. `View` holds a fifth entry, `ReClass`, after `Access Watch`.

## Working rules for agents

- Reuse existing components and theme colors before writing new UI code. Add to the component library rather than inlining.
- Do not restyle or refactor existing UI that is unrelated to the task; apply these rules to new and modified code.
- When a change affects appearance, verify it in both dark and light themes, at more than one window size, and at more than one scale factor.
- If a rule here conflicts with what a task requires, follow the task and mention the conflict instead of silently deviating.
